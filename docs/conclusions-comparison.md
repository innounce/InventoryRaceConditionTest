# 並發控制機制總比較

## 測試環境

- 情境 A：1000 個並發 stock-out ×1，初始庫存 1000
- 情境 B：1000 個並發 stock-out ×1，初始庫存 100
- 情境 C：5 秒持續壓力，50 並發，stock-in / stock-out 隨機混合，初始庫存 500
- 所有情境跑在同一台機器（in-process WebApplicationFactory），結果具有相對可比性

## 核心洞察

### 1. 正確性與吞吐量的取捨是機制選擇的主軸

所有機制都能保證正確性；差別在於「失敗的請求是被丟棄還是排隊」：

- **丟棄型**（樂觀鎖、Serializable、Redis 0ms）：衝突立即回 409，吞吐量低，客戶端需 retry
- **排隊型**（悲觀鎖、Redis 5s、Queue）：衝突等待，吞吐量高，客戶端無需 retry

### 2. TPS 上限由臨界區決定，不由鎖機制決定

任何序列化機制的吞吐量上限都是：

```
最大 TPS（單一 key）= 1 / 臨界區執行時間 ≈ 1 / 5ms = 200 TPS
```

Redis 再快、Queue 再輕，都無法突破這個上限。差別只在排隊開銷的大小。

### 3. 悲觀鎖的代價是 DB 連線池，Redis / Queue 把等待移出連線池

悲觀鎖等待期間持有 DB 連線，N 個等待者佔 N 個連線；連線池耗盡時無關的查詢也受影響。
Redis 鎖和 Queue 的等待都在 DB 之外，連線只在「真正執行工作」時才取出。

### 4. Queue 是最高吞吐量，但不能橫向擴展

`Channel<T>` 的切換開銷趨近於零，沒有輪詢間隔、沒有網路往返，所以吞吐量最高。
但 Channel 住在 process 記憶體，多台 server 各有獨立 Channel，無法跨伺服器序列化。
要擴展，需把 Channel 替換成 Redis Streams / Kafka，並接受架構從同步轉為非同步。

### 5. Redis Timeout 直接控制「成功率 vs 尾延遲」的取捨

```
timeout = 0ms  → 立即失敗，低吞吐，低延遲
timeout = 500ms → 暴衝 A 24/1000，尾延遲 P99 ≤ 500ms
timeout = 5s   → 暴衝 A 946/1000，尾延遲 P99 ≤ 5s
```

這是唯一可以在不改架構的情況下動態調整吞吐量與延遲的參數。

## 選擇建議

| 場景 | 建議機制 |
|------|---------|
| 衝突率低（正常業務）| 樂觀鎖 |
| 衝突率高、需要高成功率、單 DB 部署 | 悲觀鎖 |
| 不想寫 raw SQL、可接受中等吞吐量 | Serializable Isolation |
| 多台 server、DB 連線池友好、可接受 Redis | Redis 分散式鎖 + timeout |
| 單台 server、最高吞吐量、無外部依賴 | Queue 序列化 |
| 預期超高並發（秒殺）| 業務層提前排隊（預先抽籤 / 預約制）|
