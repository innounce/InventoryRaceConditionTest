# 並發控制機制總比較

## 測試環境

- 情境 A：1000 個並發 stock-out ×1，初始庫存 1000（Lost Update 壓力）
- 情境 B：1000 個並發 stock-out ×1，初始庫存 100（負庫存壓力）
- 情境 C：5 秒持續壓力，50 並發，stock-in / stock-out 隨機混合，初始庫存 500
- 所有情境跑在同一台機器（in-process WebApplicationFactory），結果具有相對可比性
- minSuccessLatencyMs：所有成功請求裡最短的端到端延遲，近似「臨界區最快執行時間」

---

## 情境 A — Lost Update（暴衝 1000 req，初始庫存 1000）

| 機制 | successCount | P50 (ms) | P99 (ms) | minSuccess (ms) | 正確性 |
|------|-------------|----------|----------|-----------------|--------|
| Baseline（無鎖）| 1000 / 1000 | 1523.8 | 2601.3 | 564.6 | ❌ 資料損毀 |
| 樂觀鎖 | 1 / 1000 | 653.8 | 711.9 | 557.8 | ✓ |
| Serializable Isolation | 36 / 1000 | 709.2 | 1010.2 | 448.8 | ✓ |
| Redis 分散式鎖（0ms）| 1 / 1000 | 109.0 | 127.4 | 382.8 | ✓ |
| Redis 分散式鎖（500ms）| 39 / 1000 | 566.1 | 584.0 | 369.6 | ✓ |
| Redis 分散式鎖（5s）| 947 / 1000 | 2845.6 | 5056.1 | 361.0 | ✓ |
| 悲觀鎖 | 1000 / 1000 | 1679.2 | 2910.5 | 381.6 | ✓ |
| Queue 序列化 | 1000 / 1000 | 1677.0 | 2893.9 | 310.9 | ✓ |

**說明：** Baseline 全部成功但資料損毀（lost update，最終庫存不為 0）。樂觀鎖和 Redis 0ms 只有 1 筆成功（第一波搶到後其餘立即衝突）。Serializable Isolation 僅 36 筆成功，是 SSI 在高衝突下誤殺（false abort）了本來不衝突的交易。悲觀鎖和 Queue 讓所有 1000 筆序列化完成，成功率 100%。

## 情境 B — 超量成功／負庫存風險（暴衝 1000 req，初始庫存 100）

| 機制 | successCount | P50 (ms) | P99 (ms) | minSuccess (ms) | 正確性 |
|------|-------------|----------|----------|-----------------|--------|
| Baseline（無鎖）| **241** / 1000（超出！）| 1146.4 | 1885.8 | 335.7 | ❌ race condition，超量成功 |
| Redis 分散式鎖（0ms）| 2 / 1000 | 86.0 | 105.5 | 33.1 | ✓ |
| 樂觀鎖 | 21 / 1000 | 1095.1 | 1573.8 | 290.8 | ✓ |
| Redis 分散式鎖（500ms）| 85 / 1000 | 514.4 | 547.7 | 14.0 | ✓ |
| Serializable Isolation | 47 / 1000 | 749.8 | 1269.0 | 92.8 | ✓ |
| 悲觀鎖 | **100** / 1000（滿）| 554.0 | 954.4 | 197.1 | ✓ |
| Redis 分散式鎖（5s）| **100** / 1000（滿）| 1631.1 | 3134.7 | 17.7 | ✓ |
| Queue 序列化 | **100** / 1000（滿）| 546.8 | 806.3 | 54.6 | ✓ |

**說明：** Baseline 允許 241 筆成功，比初始庫存多出 141 筆（race condition 讓多個請求同時讀到 "庫存 > 0"）。Serializable Isolation 雖然正確但只有 47 筆成功，因為 PostgreSQL SSI 存在誤殺（false abort）。悲觀鎖、Redis 5s 和 Queue 三者精確達到 100 筆，無一多餘。

## 情境 C — 對帳一致性（5 秒持續壓力，50 並發）

| 機制 | totalRequests | successCount | 成功率 | P50 (ms) | P99 (ms) | minSuccess (ms) | 對帳 |
|------|--------------|-------------|--------|----------|----------|-----------------|------|
| Baseline（無鎖）| 2,791 | 900 | 32.2% | 57.3 | 518.9 | 18.3 | ❌ |
| 樂觀鎖 | 3,371 | 183 | 5.4% | 78.0 | 142.4 | 5.5 | ✓ |
| Serializable Isolation | 3,456 | 231 | 6.7% | 74.1 | 113.1 | 30.0 | ✓ |
| Redis 分散式鎖（0ms）| **46,602** | 332 | 0.7% | 2.8 | 19.0 | 5.1 | ✓ |
| 悲觀鎖 | 5,779 | 646 | 11.2% | 16.8 | 658.9 | 5.3 | ✓ |
| Redis 分散式鎖（500ms）| 1,901 | 1,453 | 76.4% | 3.8 | 506.0 | 2.4 | ✓ |
| Redis 分散式鎖（5s）| 2,414 | 2,138 | 88.6% | 2.1 | 2506.6 | 17.7 | ✓ |
| Queue 序列化 | 2,397 | 2,162 | **90.2%** | 104.0 | 185.8 | 8.6 | ✓ |

**說明：**
- **情境 C 的 totalRequests 不能跨機制直接比較**：RunSustainedAsync 在每筆請求完成後立刻發出下一筆（包含失敗），因此失敗越快 totalRequests 越高。Redis 0ms 在 5 秒內發出 46,602 筆，但絕大多數在 2.8ms 內失敗。
- Queue P50 = 104ms 是因為所有請求都進入單一 Channel 序列化執行，看起來慢，但實際上是「每筆都成功」。
- 悲觀鎖 P99 = 658.9ms，尾延遲高於 Queue，因為大量請求堆在 DB 的 FOR UPDATE 鎖上排隊。

## 核心洞察

### 1. 臨界區時間（約 5ms）決定吞吐上限，不是鎖機制

minSuccessLatencyMs 在各機制之間差異不大（5–18ms），因為它衡量的是最快路徑：
- 取鎖成功 → 讀 DB → 寫 DB → 寫交易記錄 → 釋放鎖

這個 ~5ms 就是每一筆成功請求佔用臨界資源的時間。最大 TPS（單一 key）：

```
最大 TPS = 1 / 臨界區時間 ≈ 1 / 5ms = 200 TPS
```

所有序列化機制的吞吐量天花板都在這裡，差別只在「排隊等待的開銷和位置」。

### 2. 正確性 vs 吞吐量的分界不是機制種類，而是「丟棄 vs 排隊」

- **丟棄型**（樂觀鎖、Serializable、Redis 0ms）：衝突立即失敗，吞吐量低，客戶端需 retry。適合衝突率本來就低的業務場景。
- **排隊型**（悲觀鎖、Redis 5s、Queue）：衝突等待，吞吐量高，客戶端無需 retry。適合衝突率高、且業務上可接受等待的場景。

### 3. 悲觀鎖的代價是 DB 連線池壓力

悲觀鎖等待期間持有 DB 連線。情境 A 1000 個請求同時鎖，P99 達 2910ms；若系統其他查詢需要連線，會被這些等待者擠掉。Redis 鎖和 Queue 把等待移出 DB 連線池，對其他業務影響較小。

### 4. Redis timeout 是可動態調整的旋鈕

情境 A 的成功數從 1（0ms）→ 39（500ms）→ 947（5s），只是改了一個 timeout 值。這是在不改架構的情況下唯一能線上調整「成功率 vs 尾延遲」的參數。

### 5. Queue 單機最高，橫向擴展需換架構

`Channel<T>` 沒有輪詢間隔、沒有網路往返，情境 C 吞吐量最高（90.2% 成功率）且尾延遲最穩定（P99=185.8ms）。但 Channel 住在 process 記憶體，多台 server 各有獨立 Channel，無法跨伺服器序列化。要擴展必須把 Channel 替換成 Redis Streams / Kafka，並接受從同步 API 轉為非同步通知的架構變化。

### 6. Serializable Isolation 的誤殺問題

PostgreSQL SSI（Serializable Snapshot Isolation）在高衝突下會誤殺本來不衝突的交易（false abort）。情境 B 僅 47 筆成功（而非理論上的 100 筆），代表有 53 筆交易被誤殺。這在有重試邏輯的場景下可以吸收，但在無重試的情境下浪費吞吐量。

## 選擇建議

| 場景 | 建議機制 |
|------|---------|
| 衝突率低（正常業務流量）| 樂觀鎖 + 客戶端 retry |
| 衝突率高、需精確成功、單 DB 部署 | 悲觀鎖 |
| 多台 server、DB 連線池友好、可接受 Redis | Redis 分散式鎖（timeout 5s）|
| 單台 server、最高吞吐量、無外部依賴 | Queue 序列化 |
| 不想動程式碼、能接受中等成功率 | Serializable Isolation |
| 預期超高並發（秒殺、搶票）| 業務層提前排隊（預先抽籤 / 預約制）|
