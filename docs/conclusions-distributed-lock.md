# 分散式鎖（Redis）結論

## 機制摘要

在 `StockInAsync` / `StockOutAsync` 讀取庫存前，先對 Redis 以原子命令 `SET key token NX PX expiry` 取得分散式鎖。寫入完成後透過 Lua 腳本比對 token 再刪除，確保只有持鎖者才能釋放鎖。鎖的 key 以 `inventory:lock:{productId}` 為粒度，不同商品互不干擾。若鎖無法取得（timeout = 0），立即回傳 HTTP 409。

## 測試結果

| 情境 | 初始庫存 | 請求數 | 成功數 | 最終庫存 | Version | 交易筆數 |
|------|----------|--------|--------|----------|---------|---------|
| A Lost Update | 1,000 | 1,000 | 1 | 999 | 1 | 1 |
| B 負庫存 | 100 | 1,000 | 2 | 98 | 2 | 2 |
| C 混合持續壓力（5s, 50 並發） | 500 | — | — | 252 | 338 | 338 |

**三個情境全部通過。** 正確性指標：

- `version == successCount`（A: 1==1, B: 2==2）→ 無 lost update
- `finalQuantity >= 0`，`successCount <= initialQuantity`（B）→ 無負庫存
- `expectedQuantity == finalQuantity`（C: 500 + Σ 有號交易 = 252）→ 對帳完全吻合

## 與其他機制的比較

| 特性 | 樂觀鎖 | 悲觀鎖 | 可序列化隔離 | **分散式鎖（Redis）** |
|------|--------|--------|--------------|----------------------|
| 正確性 | ✓ | ✓ | ✓ | ✓ |
| 鎖的位置 | 資料庫行版本 | 資料庫行鎖 | 資料庫交易層 | Redis（應用層） |
| 等待方式 | 無等待，直接 409 | DB 排隊等待 | DB 排隊等待 | 無等待，直接 409 |
| 連線池壓力 | 低（短暫持連線） | 高（持連線等待） | 中（持連線等待） | **低（DB 連線不排隊）** |
| 跨 DB 伺服器 | ✓ | ✓ | ✓ | ✓（需 Redis） |
| 跨應用伺服器 | ✓ | ✓ | ✓ | ✓（需 Redis） |
| 額外基礎設施 | 無 | 無 | 無 | **需要 Redis** |
| 暴衝下吞吐量 | 低（大量 409） | 高（等待後成功） | 高（等待後成功） | **低（大量 409）** |
| 持續壓力下吞吐量 | 低 | 高 | 高 | **中（取決於鎖持有時間）** |

## 關鍵觀察

### 情境 A / B：瞬間暴衝下成功率極低

1,000 個請求同時打到同一商品，因為 Redis 鎖不等待（`timeout = default = 0`），只有第一個到達的請求拿到鎖，其餘 999 個立即收到 HTTP 409。這與樂觀鎖行為相似——正確，但吞吐量很低。

若要提升暴衝成功率，可在 `TryAcquireAsync` 加 `timeout`，讓失敗者在 Redis 層輪詢等待（不佔 DB 連線），這正是分散式鎖相較悲觀鎖的優勢所在。

### 情境 C：持續負載下表現較好

5 秒內 50 並發持續發送，完成 338 筆交易（約 68 TPS）。由於請求是持續分佈而非瞬間暴衝，鎖競爭較少，成功率明顯高於 A/B。

### 為何不佔 DB 連線池

悲觀鎖（`SELECT ... FOR UPDATE`）持有 DB 連線等待行鎖釋放，100 個並發等待就佔掉 100 個連線。分散式鎖把等待移到 Redis：DB 連線只在「已持鎖」後才取出，用完即釋放，連線池壓力大幅降低。

### 鎖超期（Expiry）自癒

`LockExpiry = 10 秒`。若持鎖的程序在寫入前崩潰，Redis 的 TTL 機制 10 秒後自動解鎖，不會造成永久死鎖。Lua 釋放腳本確保只有持鎖者（token 比對）才能刪除 key，防止慢請求釋放掉已過期、被別人重新持有的鎖。

## 適用場景

| 適合 | 不適合 |
|------|--------|
| 多台 API 伺服器橫向擴展 | 沒有 Redis 的環境（多一個故障點） |
| 需要 DB 連線池友好（高連線壓力環境） | 需要高暴衝成功率（應改用悲觀鎖 + 等待，或加 timeout 重試） |
| 鎖粒度細（不同商品完全並行） | Redis 本身不可用時整個寫入路徑癱瘓 |
| 鎖邏輯跨多個 DB（跨資料庫事務）| |

## 結論

Redis 分散式鎖在**正確性**上與悲觀鎖、可序列化隔離等效。核心優勢是把鎖等待從資料庫連線池移走，在多伺服器部署下對 DB 連線壓力更友好。代價是引入了 Redis 作為額外依賴——Redis 不可用時鎖無法取得，整個庫存寫入路徑會失敗。

在本測試的「零等待」設定下，暴衝場景成功率很低（與樂觀鎖相當）；若加上適當的 `timeout` 讓客戶端在 Redis 層輪詢，可以在不佔用 DB 連線的前提下大幅提升成功率，兼顧正確性與吞吐量。
