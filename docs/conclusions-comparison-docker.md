# 並發控制機制總比較（Docker 環境）

## 測試環境

- **資料庫**：PostgreSQL 18（Docker，無持久化，port 5434）
- **Redis**：Redis 7-alpine（Docker，port 6381）
- **對照版本**：`docs/conclusions-comparison.md` 為 PostgreSQL 17 本機實體數據
- 情境 A：1000 個並發 stock-out ×1，初始庫存 1000（Lost Update 壓力）
- 情境 B：1000 個並發 stock-out ×1，初始庫存 100（負庫存壓力）
- 情境 C：5 秒持續壓力，50 並發，stock-in / stock-out 隨機混合，初始庫存 500
- 所有情境跑在同一台機器（in-process WebApplicationFactory），結果具有相對可比性
- minSuccessLatencyMs：所有成功請求裡最短的端到端延遲，近似「臨界區最快執行時間」

## 情境 A — Lost Update（暴衝 1000 req，初始庫存 1000）

| 機制 | successCount | P50 (ms) | P99 (ms) | minSuccess (ms) | 正確性 |
|------|-------------|----------|----------|-----------------|--------|
| Baseline（無鎖）| 1000 / 1000 | 1562.1 | 2707.3 | 497.6 | ❌ 資料損毀 |
| 樂觀鎖 | 1 / 1000 | 584.9 | 675.8 | 506.7 | ✓ |
| Serializable Isolation | 30 / 1000 | 735.8 | 1067.6 | 407.5 | ✓ |
| Redis 分散式鎖（0ms）| 1 / 1000 | 114.9 | 137.2 | 373.3 | ✓ |
| Redis 分散式鎖（500ms）| 42 / 1000 | 558.0 | 581.2 | 336.1 | ✓ |
| Redis 分散式鎖（5s）| 926 / 1000 | 2939.9 | 5070.7 | 325.4 | ✓ |
| 悲觀鎖 | 1000 / 1000 | 1728.3 | 3138.5 | 361.3 | ✓ |
| Queue 序列化 | 1000 / 1000 | 1715.9 | 2943.9 | 309.2 | ✓ |

**說明：** Baseline 全部成功但資料損毀（lost update，最終庫存不為 0）。樂觀鎖和 Redis 0ms 只有 1 筆成功（第一波搶到後其餘立即衝突）。Serializable Isolation 僅 30 筆成功，是 SSI 在高衝突下誤殺（false abort）了本來不衝突的交易。悲觀鎖和 Queue 讓所有 1000 筆序列化完成，成功率 100%。

## 情境 C — 對帳一致性（5 秒持續壓力，50 並發）

| 機制 | totalRequests | successCount | 成功率 | P50 (ms) | P99 (ms) | minSuccess (ms) | 對帳 |
|------|--------------|-------------|--------|----------|----------|-----------------|------|
| Baseline（無鎖）| 3,812 | 905 | 23.7% | 26.6 | 497.0 | 22.9 | ❌ |
| 樂觀鎖 | 3,348 | 118 | 3.5% | 81.8 | 124.6 | 16.5 | ✓ |
| Serializable Isolation | 3,697 | 174 | 4.7% | 77.3 | 115.2 | 32.0 | ✓ |
| Redis 分散式鎖（0ms）| **44,429** | 305 | 0.7% | 2.8 | 19.2 | 9.0 | ✓ |
| 悲觀鎖 | 6,739 | 734 | 10.9% | 9.6 | 694.1 | 15.6 | ✓ |
| Redis 分散式鎖（500ms）| 1,827 | 1,355 | 74.2% | 4.2 | 509.6 | 2.7 | ✓ |
| Redis 分散式鎖（5s）| 2,254 | 2,000 | 88.7% | 2.3 | 2121.1 | 1.4 | ✓ |
| Queue 序列化 | 2,242 | 2,027 | **90.4%** | 115.6 | 149.6 | 17.8 | ✓ |

**說明：**
- **情境 C 的 totalRequests 不能跨機制直接比較**：RunSustainedAsync 在每筆請求完成後立刻發出下一筆（包含失敗），因此失敗越快 totalRequests 越高。Redis 0ms 在 5 秒內發出 44,429 筆，但絕大多數在 2.8ms 內失敗。
- Queue P50 = 115.6ms 是因為所有請求都進入單一 Channel 序列化執行，看起來慢，但實際上是「每筆都成功」。
- 悲觀鎖 P99 = 694.1ms，尾延遲高於 Queue，因為大量請求堆在 DB 的 FOR UPDATE 鎖上排隊。

## 核心洞察

### 1. 臨界區時間（約 5ms）決定吞吐上限，不是鎖機制

minSuccessLatencyMs 在各機制之間差異不大（1–17ms），因為它衡量的是最快路徑：
- 取鎖成功 → 讀 DB → 寫 DB → 寫交易記錄 → 釋放鎖

這個 ~5ms 就是每一筆成功請求佔用臨界資源的時間。最大 TPS（單一 key）：

```
最大 TPS = 1 / 臨界區時間 ≈ 1 / 5ms = 200 TPS
```

所有序列化機制的吞吐量天花板都在這裡，差別只在「排隊等待的開銷和位置」。

### 2. 正確性 vs 吞吐量的分界不是機制種類，而是「丟棄 vs 排隊」

- **丟棄型**（樂觀鎖、Serializable、Redis 0ms）：衝突立即失敗，吞吐量低，客戶端需 retry。適合衝突率本來就低的業務場景。
- **排隊型**（悲觀鎖、Redis 5s、Queue）：衝突等待，吞吐量高，客戶端無需 retry。適合衝突率高、且業務上可接受等待的場景。

### 3. 悲觀鎖的代價是 DB 連線池壓力

悲觀鎖等待期間持有 DB 連線。情境 A 1000 個請求同時鎖，P99 達 3138.5ms；若系統其他查詢需要連線，會被這些等待者擠掉。Redis 鎖和 Queue 把等待移出 DB 連線池，對其他業務影響較小。

### 4. Redis timeout 是可動態調整的旋鈕

情境 A 的成功數從 1（0ms）→ 42（500ms）→ 926（5s），只是改了一個 timeout 值。這是在不改架構的情況下唯一能線上調整「成功率 vs 尾延遲」的參數。

### 5. Queue 單機最高，橫向擴展需換架構

`Channel<T>` 沒有輪詢間隔、沒有網路往返，情境 C 吞吐量最高（90.4% 成功率）且尾延遲最穩定（P99=149.6ms）。但 Channel 住在 process 記憶體，多台 server 各有獨立 Channel，無法跨伺服器序列化。要擴展必須把 Channel 替換成 Redis Streams / Kafka，並接受從同步 API 轉為非同步通知的架構變化。

### 6. Serializable Isolation 的誤殺問題

PostgreSQL SSI（Serializable Snapshot Isolation）在高衝突下會誤殺本來不衝突的交易（false abort）。情境 A 僅 30 筆成功、情境 B 僅 33 筆，在無重試的情境下浪費吞吐量顯著。

## 選擇建議

| 場景 | 建議機制 |
|------|---------|
| 衝突率低（正常業務流量）| 樂觀鎖 + 客戶端 retry |
| 衝突率高、需精確成功、單 DB 部署 | 悲觀鎖 |
| 多台 server、DB 連線池友好、可接受 Redis | Redis 分散式鎖（timeout 5s）|
| 單台 server、最高吞吐量、無外部依賴 | Queue 序列化 |
| 不想動程式碼、能接受中等成功率 | Serializable Isolation |
| 預期超高並發（秒殺、搶票）| 業務層提前排隊（預先抽籤 / 預約制）|
