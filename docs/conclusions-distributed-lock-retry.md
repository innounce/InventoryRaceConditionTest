# 分散式鎖（Redis + 等待重試）結論

## 與前一版本的差異

本分支基於 `feature/distributed-lock`，唯一改動是在 `InventoryService.AcquireLockAsync` 呼叫
`TryAcquireAsync` 時傳入 `LockTimeout = 500ms`。`RedisDistributedLockFactory` 的輪詢迴圈
（每 5ms 重試一次 `SET NX`）本來就已支援，無需修改鎖工廠本身。

```csharp
// 前一版（無等待）
var lock_ = await lockFactory.TryAcquireAsync(key, LockExpiry);

// 本版（Redis 層等待最多 500ms）
var lock_ = await lockFactory.TryAcquireAsync(key, LockExpiry, LockTimeout);
```

## 測試結果對比

| 情境 | 初始庫存 | 請求數 | 無等待 successCount | **有等待 successCount** | 倍數 |
|------|----------|--------|---------------------|-------------------------|------|
| A Lost Update | 1,000 | 1,000 | 1 | **24** | 24× |
| B 負庫存 | 100 | 1,000 | 2 | **77** | 38× |
| C 混合持續（5s, 50 並發） | 500 | — | 338 筆 | **1,343 筆** | 4× |

**三個情境全部通過，正確性不變：**

- A: `finalQuantity (976) == 1000 - 24`，`version (24) == successCount (24)` ✓
- B: `finalQuantity (23) >= 0`，`successCount (77) <= 100`，`23 == 100 - 77` ✓
- C: `500 + Σ 有號交易 = 1`（finalQuantity），對帳完全吻合 ✓

## 為什麼吞吐量差距這麼大

### 無等待版（timeout=0）
1000 個請求同時打到 Redis，只有第 1 個拿到鎖，其餘 999 個立即收到 HTTP 409 並放棄。
後續根本不會再進入資料庫。

### 有等待版（timeout=500ms）
無法立即拿到鎖的請求在 Redis 層輪詢（每 5ms 嘗試一次），**等待期間不持有 DB 連線**。
每筆請求的 DB 寫入約需 5–10ms，因此 500ms 視窗內可依序通過約 50–100 個請求。
實測情境 A 拿到 24 個（暴衝起點的排隊競爭讓實際略低於理論上限）。

情境 C 改善幅度（4×）相對小，因為原本 50 並發的持續壓力就比 1000 暴衝的競爭程度低，
加了 retry 後等待時間主要花在鎖的解放週期，效益相對均勻。

## DB 連線池優勢：與悲觀鎖的關鍵差異

```
悲觀鎖等待路徑：
請求 → 取得 DB 連線 → [等待行鎖，連線被佔] → 讀-改-寫 → 釋放連線

分散式鎖等待路徑：
請求 → [在 Redis 輪詢，不佔 DB 連線] → 取得 Redis 鎖 → 取得 DB 連線 → 讀-改-寫 → 釋放連線 → 釋放 Redis 鎖
```

悲觀鎖在等待期間佔住連線，N 個並發等待者就消耗 N 個連線，連線池容易被壓垮。
分散式鎖的等待完全在 Redis（記憶體操作，微秒級），只有真正拿到鎖才取 DB 連線，
連線池壓力恆等於「同時執行中的請求數」，與等待佇列長度無關。

## 各機制吞吐量總覽（情境 A，1000 並發 stock-out）

| 機制 | successCount | 說明 |
|------|-------------|------|
| Baseline（無鎖） | ~900+ | 正確性完全失守 |
| 樂觀鎖 | 個位數 | 衝突即 409，無重試 |
| 悲觀鎖 | ~1000 | 等待佔 DB 連線 |
| 可序列化隔離 | ~1000 | 等待佔 DB 連線 |
| Redis 分散式鎖（無等待）| **1** | 立即 409 |
| **Redis 分散式鎖（500ms retry）** | **24** | Redis 層排隊，DB 連線友好 |

> 悲觀鎖 / 可序列化隔離的高成功數來自 DB 層的等待佇列；代價是連線池壓力。
> Redis retry 版在測試環境下達到 24，在生產環境（鎖持有時間更短）可期待更高。

## 調參空間

| 參數 | 本版設定 | 調整方向 |
|------|----------|----------|
| `LockTimeout` | 500ms | 調高 → 更多請求成功但 P99 延遲上升；調低 → 更快失敗 |
| 輪詢間隔 | 5ms（固定）| 改指數退避（5→10→20ms）可減少 Redis 空轉 |
| `LockExpiry` | 10s | 依最慢 DB 寫入預估，過短會讓慢請求的鎖提早失效 |

## 結論

加入 500ms 等待重試後，暴衝場景吞吐量提升 **24–38 倍**，持續壓力場景提升 **4 倍**，
且正確性完全保持。等待完全在 Redis 記憶體層發生，對 DB 連線池的壓力與悲觀鎖相比
仍有結構性優勢。

這是分散式鎖相較於純 DB 鎖的核心價值：**把等待成本從稀缺資源（DB 連線）轉移到
廉價資源（Redis 記憶體輪詢）**，讓兩者各司其職。
